# CR-002 — MCP サーバを廃止し、Oracle へのアクセスを backend(FastAPI)に統合する

## 起票日

2026-09-27

## 起票者

プロジェクトの依頼者(Claude Code セッションでの指示、2026-09-27)。原文: 「Oracle DB へのアクセスを MCP で実現するように指示していましたが、その必要がないと判断しました。MCP の部分は廃止して、バックエンド(Python FastAPI) に統合してください。」

## 背景・課題

* 第 1 リリースでは、人間の指示により Oracle へのアクセスを **すべて MCP サーバ(FastMCP、stdio)経由** にしている(P001 §3.1、ADR-001)。backend(FastAPI)は MCP サーバを子プロセスとして起動し、MCP クライアントとしてツール(`get_schema_snapshot`・`get_table_rows`・`ping`)を呼ぶ。backend は Oracle に直接接続しない。
* 依頼者は、この MCP 経由の構成は不要と判断した。MCP を挟むことで、子プロセスの管理(起動・再起動・stdio の標準出力の扱い)、MCP のエラー → API のエラーへの変換、MCP 用の設定(`mcp_call_timeout_sec`)、MCP 固有のテスト(T05・T09 など)が余計に必要になっている。

## 変更要求の内容

* MCP サーバ(`server/src/dbfaq_mcp`、FastMCP)と、backend 側の MCP クライアント(`server/src/dbfaq_api/mcp_gateway.py`)を廃止する。
* Oracle へのアクセス(接続プール、読み取り専用トランザクション、データディクショナリの問い合わせ、スナップショットの組み立て、テーブルデータのページ取得、セル値の文字列化、識別子の検証とクォート、Oracle エラーの変換)を backend(`dbfaq_api`)のプロセス内に移す。処理の中身(発行する SQL、読み取り専用トランザクション、識別子の扱い、値の表示形式)は変えない。
* 依存から `fastmcp` を外す。設定 `app.mcp_call_timeout_sec` を廃止する。
* 画面の機能・表示は変えない。API は、MCP の廃止にともなって意味を失う部分だけを変える。
  * `GET /api/health` の応答から `mcp` を除く。`status` は `oracle` だけで決める。
  * エラーコード `MCP_UNAVAILABLE`(503)を廃止する(発生しなくなる)。
* 関係する仕様: `docs/P001-requirement.md` §3.1・§3.3・§6・§7・§7.1・§8.2・§8.3・§8.5・§9・§10、`docs/P002-frontend-spec.md` §3.1・§3.3・§3.5・§3.7・§5、`docs/P003-backend-spec.md` 全般、`docs/ADR.md` ADR-001 ほか。

## 期待する振る舞い

* `server/src/dbfaq_mcp` と `mcp_gateway.py` が無く、`server/pyproject.toml` の依存に `fastmcp` が無い。
* api コンテナの中で `dbfaq_mcp` の子プロセスが動いていない(api のプロセスは uvicorn だけ)。
* 「Oracle から再読み込み」で HR のスキーマを読み込むと、これまでと同じ内容(7 テーブル、外部キー 10 本、自己参照 EMP_MANAGER_FK、インデックス 19 など)が SQLite に保存され、ER 図に表示される。
* データタブで EMPLOYEES を開くと、これまでと同じ並び順・値の表示で 1 ページ 50 行ずつページ送りできる。
* Oracle へのアクセスはすべて読み取り専用トランザクションの中で行われ、最後に必ずロールバックされる(受入テストの前後で HR のチェックサムが一致する)。
* Oracle に届かない設定でも api は起動し、ER 図とスキーマ情報タブは表示でき、再読み込みとデータタブは Oracle のエラーを返す。Oracle が戻れば、api を再起動せずに再読み込み・データタブが使えるようになる。
* `GET /api/health` の応答に `mcp` が無く、Oracle に届くときは `status: ok`、届かないときは `status: degraded` と `oracle.message` を返す。ヘッダの Oracle 状態表示はこれまでどおり動く。
* ログは backend の標準出力に 1 行 1 JSON で出て、パスワードを含まない。
* 既存の性能目標(P001 §8.1)と同時 10 名の合格基準(P001 §8.4)を満たす。
* 単体・結合・受け入れ結合テストのスイートを 2 回続けて実行しても同じ結果になる。

## 影響が想定される範囲

* 画面: 表示・操作は変えない。frontend の型(`client/src/api/types.ts` の health)とテスト用のモックから `mcp` を除く。
* API: `GET /api/health` の `mcp` を削除、エラーコード `MCP_UNAVAILABLE` を削除。その他のエンドポイントの形は変えない。
* データモデル: 変更なし(SQLite のスナップショットの形はそのまま)。
* 設定: `config.yaml` の `app.mcp_call_timeout_sec` を廃止(残っていても無視する)。
* 構成: api コンテナの MCP 子プロセスが無くなる。Oracle の接続プールは api プロセスが持つ。
* テスト: P008 の T01〜T05・T09(MCP を前提とする結合テスト)、P009 の A04 手順 7(MCP 子プロセスの強制終了からの回復)ほか。
* 関連ADR: **ADR-001(MCP サーバを backend の子プロセス(stdio)として常駐させる)を覆す要望である。** ADR-001 は廃止になる。ADR-007(uv プロジェクト構成)・ADR-011(Oracle アクセス)・ADR-012(compose 構成)の記述も MCP を前提にしている部分を見直す。
* 将来スコープ(P001 §10)の「任意の SELECT を実行する MCP ツール」「MCP の HTTP トランスポート」は、MCP を使わない形に書き換えるか削除する。

## 優先度の判断理由

* 中。影響度: 高(Oracle へのアクセスという主要機能の実装基盤と、構成・テストの広い範囲にかかわる)。緊急度: 低(現状の MCP 経由の構成でも全機能が動いており、困っている利用者はいない)。ルーブリックで「中」。★ACCEPTED★(2026-09-27 人間承認) 検討: 依頼者から優先度の指定が無く、ルーブリックで仮置きした/承認理由: 依頼者が「中」でよいと確認した/残存リスク: 特になし

## 備考

* 「MCP サーバを単体で Claude Desktop などから使える」(P001 §3.1 の ★ACCEPTED★)も、MCP サーバの廃止とともに無くなる。依頼者の指示は「MCP の部分は廃止」であり、単体利用を残す指示は無いため、残さない。
