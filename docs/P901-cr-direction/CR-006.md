# CR-006 — 読み取り専用ユーザー dbfaq_ro を前提に、PDB 情報・ひな型を対象スキーマ基準にする。README に dbfaq_ro の作成手順を載せる

## 起票者

プロジェクトの依頼者(Claude Code セッションでの指示、2026-10-09)。経緯: 依頼者が「PDB のメタ情報を取得するための DBA 権限を持ちつつ、READ ONLY なユーザは作れますか?」と相談し、Agent が作成方法と DbFAQ への影響を回答した。依頼者が開発用 Oracle(FREEPDB1)にユーザー `dbfaq_ro` を作り(`GRANT CREATE SESSION`、`GRANT SELECT_CATALOG_ROLE`、`GRANT READ ANY TABLE ON SCHEMA hr`)、`config.yaml` の接続ユーザーを `dbfaq_ro` に変えた。Agent が `dbfaq_ro` での動作を確認して改修案(1〜5)を示したところ、依頼者の指示: 「これに加えて README.md に、このアプリDBFaq を使うにあたり Oracle DB にdbfaq_ro ユーザを作る理由と、その作り方、および config.yaml へ登録することを載せてください。」

## 背景・課題

* CR-005 の PDB 画面とひな型は、接続ユーザーが対象スキーマの所有者(`hr`)であることを前提に USER_* ビューを使っている。読み取り専用ユーザー `dbfaq_ro` で接続すると、PDB 情報の「表領域の割り当て」「セグメントの使用量」と、ひな型 02・03・08〜13 が `dbfaq_ro` 自身の分(0 行)になる(2026-10-09 確認)。
* ひな型 04(LOB、全スキーマ)は、読む権限の無い表(開発用 Oracle の APPOWNER.DOCUMENTS)があると ORA-19202 で全体が失敗する。
* 一方、`dbfaq_ro` では DBA_* ・V$ を使うひな型 01・05〜07・14〜17 と「表領域の使用状況」が動くようになった。書き込み権限が無いため、Query タブの安全性も高まる(DML は ORA-41900 の権限エラーで止まる)。
* 利用者が DbFAQ を導入するとき、読み取り専用ユーザーを作る理由と手順が README に無い。

## 変更要求の内容

* DbFAQ の推奨の接続ユーザーを、読み取り専用ユーザー(例 `dbfaq_ro`: `CREATE SESSION`、`SELECT_CATALOG_ROLE`、対象スキーマの表の `READ`)とする。開発・テスト用の接続ユーザーも `hr` から `dbfaq_ro` に変える(`docs/P001-requirement.md` §2・§8.3)。
* PDB 情報タブとひな型を、接続ユーザーではなく**対象スキーマ**(`config.yaml` の `oracle.schema`)を基準にする(`docs/P001-requirement.md` §6 SC-03、`docs/P002-frontend-spec.md` §3.14、`docs/P003-backend-spec.md` §3.12・§4.7)。
* ひな型 04(全スキーマの LOB)は、接続ユーザーが読める表だけを対象にし、読めない表があっても失敗しないようにする。
* 既に登録済みのひな型を、新しい版の SQL に更新できるようにする(利用者が変更していないものに限る)。
* README.md に、DbFAQ を使うにあたり Oracle に `dbfaq_ro` ユーザーを作る理由、作り方(SQL)、`config.yaml` への登録を載せる(依頼者の指示)。

## 期待する振る舞い

* README.md に、`dbfaq_ro` を作る理由(読み取り専用で安全、PDB 情報・運用ひな型に辞書ビューの参照権限が要る)、作成の SQL、`config.yaml` の `oracle.user`・`password`・`schema` の書き方が載っている。
* `dbfaq_ro` で接続した状態で、ER 図・スキーマ情報タブ・データタブ・Query タブ(実行・CSV・エラー位置)・保存済み Query が従来どおり使える。
* `dbfaq_ro` で接続した状態で、PDB 情報タブの概要に接続ユーザー `DBFAQ_RO` と対象スキーマ `HR` が表示され、「表領域の割り当て」「セグメントの使用量」に HR の分が表示され、「表領域の使用状況」が表示される(権限エラーにならない)。
* `dbfaq_ro` で接続した状態で、ひな型 17 件がすべて成功する。03 と 04 の結果に `EMPLOYEE_FIGURE.FIGURE` の行があり、04 は読めない表(APPOWNER.DOCUMENTS)があっても失敗しない。
* Query タブで、スキーマ名を付けない表名(例 `SELECT * FROM EMPLOYEES`)が対象スキーマの表として実行できる。
* 既存の環境(CR-005 のひな型が登録済み)で backend を新しい版で起動すると、利用者が変更していないひな型は新しい版の SQL になり、利用者が変更したひな型はそのまま残る。
* `dbfaq_ro` で DML を送っても、データは変わらない(Query の検査で拒否される。検査を通らない経路でも権限エラーまたは読み取り専用トランザクションで拒否される)。

## 影響が想定される範囲

P901時点での見積もりであり、確定した対応範囲ではない(確定は P903 が `docs/P903-cr-records/CR-006.md` に記録する)。

* 画面: SC-03 の PDB 情報タブの項目名(「接続ユーザー」→「対象スキーマ」)。ひな型の名前・説明

* データモデル: 変更なし(ひな型の更新は既存の `saved_queries`・`query_template_seeds` の範囲で行う見込み)
