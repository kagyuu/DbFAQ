# CR-009 — LLM で SQL を作る機能には性能を求めない。時間がかかっても正しく SQL が作られることだけを検証する

## 起票日

2026-10-14

## 起票者

プロジェクトの依頼者(Claude Code セッションでの指示、2026-10-14)。原文: 「またLLMの性能についても、LLMに依存することで、かつSQLをLLMに作らせる機能はオマケなので、気にしなくてもいいです。時間がかかっても正常にQueryが生成されることだけを検証してください。」

## 背景・課題

* CR-007 で LLM で SQL を作る機能に性能の目標(LLM の処理時間 + 1 秒以内)と、応答を待つ上限(既定 180 秒、nginx 300 秒)を置いた。開発環境の Ollama(CPU)では 1 回 60〜100 秒かかり、上限に対する余裕が小さい。
* 依頼者の判断: LLM の性能は LLM に依存し、この機能はオマケなので、性能は気にしない。時間がかかっても正しく SQL が作られることを検証する。

## 変更要求の内容

* LLM で SQL を作る機能の性能の目標をやめる(`docs/P001-requirement.md` §8.1)。
* 時間がかかっても作成が途中で打ち切られないよう、LLM の応答を待つ上限を延ばす(`config.yaml` の `llm.timeout_sec` の既定、nginx の `/api/llm/` の待ち時間)(`docs/P003-backend-spec.md` §2.1・§6)。
* LLM のテスト(T16・A11)は、かかった時間では判定せず、時間がかかっても SQL が作られ、検査に通り、実行できることだけを判定する(`docs/P006-test-plan.md` §3.1)。

## 期待する振る舞い

* 要件定義に、LLM で SQL を作る機能の性能の目標が無い(性能を求めないことが書かれている)。
* LLM の応答に数分かかっても、既定の設定では作成が打ち切られず、SQL が入力欄に入る。
* T16・A11 は、LLM の応答にかかった時間によって不合格にならない(十分に長い待ち時間で、SQL が作られて実行できることを判定する)。
* 作成中の表示が、時間がかかりうることを伝える。
* その他の振る舞い(LLM の状態の表示、ボタンの無効化、LLM とのやりとり、他の機能の性能の目標)は変わらない。

## 影響が想定される範囲

P901時点での見積もりであり、確定した対応範囲ではない(確定は P903 が `docs/P903-cr-records/CR-009.md` に記録する)。

* 画面: 作成中の表示の文言
* API: 変更なし
* 設定: `llm.timeout_sec` の既定(180 → 600 秒。設定できる上限)。nginx の `/api/llm/` の待ち時間(300 → 660 秒)
* テスト: T16・A11 の待ち時間と判定の基準。P006 §3.1
* 関連ADR: ADR-018(残存リスクの「生成に数十秒かかる」の扱い)。CR-007 の ★ACCEPTED★ #91(性能の目標と既定の上限)を変える

## 優先度の判断理由

* 低。影響度: 低(オマケの機能の性能の扱いだけ)。緊急度: 低。ルーブリックで「低」。★ACCEPTED★(2026-10-15 人間承認)検討: 依頼者から優先度の指定が無く、ルーブリックで仮置きした/承認理由: 依頼者「CR-009 の優先度は低でかまいません」/残存リスク: 特になし

## 備考

* 既定の待ち時間を 600 秒(`config.py` の `timeout_sec` の上限)にするのは、依頼者の「時間がかかっても」を受けた Agent の想定。それ以上かかる LLM では `LLM_TIMEOUT` になる。
* CR-008 の P201 で判明した「LLM の生成の直後は同じマシンの他の機能の性能の測定が遅くなる」(F013)は、他の機能(ER 図など)の性能の目標の問題であり、本 CR では変えない(スイートの順序で避けたまま)。
