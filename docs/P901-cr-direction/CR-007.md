# CR-007 — 自然言語の要求から LLM(Ollama)で SELECT 文を作る。LLM の稼働状況をヘッダに表示する

## 起票日

2026-10-13

## 起票者

プロジェクトの依頼者(Claude Code セッションでの指示、2026-10-13)。原文: 「次は大きな変更を入れましょう。SQLのQueryをLLMを使って、自然言語の要求仕様から作ることができるようにしてください。開発時にはLLMは、http://localhost:11434 で待ち受けしている Ollama を使ってください。モデルはgemma4:e2b-it-qatを使ってください。LLMの設定内容はConfig.yaml で設定できるようにしてください。LLMの稼働状況をメイン画面に表示してください。現在 Oracle DB の状況が緑の〇、赤の〇で表示されていますが、その並びに同様に表示してください。LLM が機能していない時には、SQLのLLMからの作成ボタンは無効化してください。なお、事前にLLMに自然言語からSQLを組み立てるにはどんな情報が必要かを尋ねてあります。」(続けて、LLM の回答「必須情報 1: データベースの構造(テーブル名と内容・列の名前と型・リレーションシップ)、必須情報 2: 具体的な要求(目的・SELECT 項目・WHERE・ORDER BY・GROUP BY)、補足情報: データ例(サンプル)・処理の制約・データベースの種類」を貼り付け)。追加の情報(同日): 「このアプリはDockerで動きますが、Dockerからホストを参照する際のIPアドレスは 172.17.0.1 になるはずです。アプリからLLMは、http://172.17.0.1:11434 で参照できるはずです。(この情報を使う場合は検証をしてください。人間は検証していません。確信はあるけど)」

## 背景・課題

* Query タブ(CR-004)では、ひな形(全列と外部キーの JOIN)から先の条件・集計・並び替えを利用者が SQL で書く必要がある。Oracle の SQL に慣れていない運用担当者には手間がかかる。
* 開発環境には Ollama(`http://localhost:11434`、モデル `gemma4:e2b-it-qat`)があり、HR のスキーマ情報を渡すと実用的な SELECT 文を返すことを確かめた(2026-10-13。1 回 17〜49 秒)。

## 変更要求の内容

* SC-02 の Query タブと SC-03 の Query タブに、自然言語の要求を入力して LLM に SELECT 文を作らせる機能を加える。作った SQL は入力欄に入れ、利用者が確かめてから実行する(`docs/P001-requirement.md` §6、`docs/P002-frontend-spec.md` §2.2.6・§2.3.3)。
* LLM に渡す情報は、依頼者が LLM から得た回答に従う: データベースの種類(Oracle とそのバージョン)、スキーマの構造(テーブルと内容の説明、列の名前・型・コメント、主キー・外部キーの関係)、利用者の要求、補足としてデータの例。
* LLM の接続先・モデルなどの設定を `config.yaml` に置く(開発時は Ollama `http://localhost:11434`、モデル `gemma4:e2b-it-qat`)(`docs/P003-backend-spec.md` §2)。
* 共通ヘッダの Oracle の状態の丸の並びに、LLM の状態の丸(緑 = 使える、赤 = 使えない)を表示する(`docs/P002-frontend-spec.md` §1.1)。
* LLM が使えないときは、LLM で SQL を作るボタンを押せなくする。
* backend に LLM で SQL を作る API を加え、`GET /api/health` に LLM の状態を加える(`docs/P002-frontend-spec.md` §3)。

## 期待する振る舞い

* `config.yaml` の `llm` の設定(接続先・モデルなど)で、使う LLM を変えられる。
* LLM(Ollama)が使えるとき、ヘッダの Oracle の丸の並びに LLM の丸が緑で表示され、マウスを乗せるとモデル名と接続先が表示される。
* LLM が使えないとき(接続できない、モデルが無い、設定が無い)、LLM の丸が赤(設定が無いときは灰)で表示され、理由が分かり、LLM で SQL を作るボタンが押せない。
* SC-02 の Query タブで自然言語の要求(例「給与の高い社員を上位 5 人、姓と部署名と給与」)を入力してボタンを押すと、そのテーブルと外部キーでつながるテーブルの構造をもとに LLM が SELECT 文を作り、入力欄に入る。そのまま実行すると結果が表示される。
* SC-03 の Query タブでも、対象スキーマと辞書ビューを前提に SELECT 文を作れる。
* LLM が作った SQL は自動では実行されず、Query の検査(SELECT・WITH の 1 文だけ)に通らないときは、実行できない旨が表示される。
* 作成中は処理中であることが表示され、LLM がエラー・時間切れのときは理由が表示される(入力欄の SQL は消えない)。
* Docker(compose)で動かしたときも、`config.yaml` または環境変数で LLM の接続先を指定して使える。
* 既存の機能(ER 図・各タブ・Query の実行・保存済み Query・PDB 画面)は変わらない。

## 備考

* 依頼者の追加情報「Docker からは `http://172.17.0.1:11434`」を 2026-10-13 に検証した: api コンテナから `172.17.0.1:11434`・`host.docker.internal:11434`・`192.168.1.12:11434` のいずれも **Connection refused**。原因: この開発環境の WSL は mirrored モードで、Ollama は Windows 側のプロセス(`ollama`)が IPv6 の `::` の 11434 番だけで待ち受けている。WSL の `localhost:11434` には届くが、Docker のブリッジや LAN の IPv4 からは届かない。依頼者に伝えた(Windows で `OLLAMA_HOST=0.0.0.0:11434` にして Ollama を再起動する案。これも未検証)。開発(WSL 上の単体・結合テスト)は `http://localhost:11434` で行う。
* 2026-10-13 追記: 依頼者が Windows で `OLLAMA_HOST=0.0.0.0:11434` を設定して Ollama を再起動したが、待ち受けは `[::]:11434` のままで、コンテナからは引き続き届かなかった(mirrored モードでは、WSL・コンテナから共有の IP(192.168.1.12)への接続は WSL 自身に届くため)。依頼者が WSL に socat をインストールし、WSL の 11435 番から `127.0.0.1:11434`(Windows の Ollama)へ中継したところ、api コンテナから `http://host.docker.internal:11435`・`http://172.17.0.1:11435` で届き、チャットの応答も得られた(35.7 秒)。開発環境ではこの中継を使う。
