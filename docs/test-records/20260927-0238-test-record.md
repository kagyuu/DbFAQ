## A03: Oracle に届かないときのシナリオ

- 参照したテスト指示: docs/P009-acceptance-direction/A03-oracle-down-scenario.md
- 実行コマンド: `run-suite.sh` 内(`DBFAQ_ORACLE_HOST=oracle-unreachable.invalid docker compose up -d --no-deps --force-recreate api` の後に `npx playwright test tests/a03-oracle-down.spec.ts -g unreachable`)
- 結果: FAIL(手順 1)。手順 6(recovered)は PASS
- 期待結果: `/api/health` が 200、status=degraded、oracle.status=error
- 実際の結果: `/api/health` が **500 `INTERNAL_ERROR`**(`h.status` が undefined)。手で再現しても同じ(3 回とも 500)
- 失敗ログ抜粋(`docker compose logs api`): `socket.gaierror: [Errno -2] Name or service not known`(`oracledb/impl/base/connect_params.pyx` の `Address.resolve_host_name` から。プールの `acquire` の中)
- 原因: python-oracledb は、接続先のホスト名を解決できないとき `oracledb.Error` ではなく `socket.gaierror`(`OSError`)をそのまま送出する。`Database.run_readonly` は `oracledb.Error` だけを `OracleFailure` に変換しており、`/api/health` も `OracleFailure` だけを捕まえるため、500 になった。CR-002 前は MCP サーバがあらゆる例外をツールエラーに包んでいたので、health は degraded になっていた(**CR-002 による退行**)
- テスト指示との矛盾の疑い: なし(テストは P002 §3.7「常に 200」どおり)
- 次工程への申し送り: P202 で修正計画を立てる
