- 対象ブランチ/コミット: main / e0afb86 + 未コミットの作業ツリー

- 実行環境: WSL2 Linux 5.15 / docker compose(web: nginx 1.27、api: python 3.12-slim)/ Chromium(Playwright 1.63)/ Oracle 23.26.3(既存コンテナ、HR)
- 事前ビルド結果: `uv run pytest tests/unit` 131 件合格、`npm test` 54 件合格・`npm run build` 成功、`docker compose build` 成功
- 実行コマンド: `a05-perf-api.sh hr` → `playwright -g hr` → `a05-load-large.sh` → `a05-perf-api.sh large` → `playwright -g large` → `a05-restore-hr.sh`
- 結果: FAIL
- 期待結果: HR と 300 表規模の測定値がすべて目標内。測定後に HR に戻る
- 実際の結果: 測定値はすべて目標内: HR `GET /api/schema` 中央値 0.004 s、refresh 0.153 s、rows のオーバーヘッド 0.023 s、HR の ER 図表示 1 秒未満、大規模 `GET /api/schema` 中央値 0.071 s、大規模 ER 図表示 2,018 ms。ただし (1) `-g hr` が project 名 `chromium` にも一致し、大規模データ投入前に large のテストが走って FAIL、(2) `a05-restore-hr.sh` が失敗(`restore failed: 300`)
- 失敗ログ抜粋: (1) `Expected: 300 Received: 7`(投入前の実行) (2) api のログに `sqlite3.OperationalError: attempt to write a readonly database`。`docker compose cp` で入れた SQLite ファイルの所有者がホストの uid 1000 のままで、api(uid 10001)が書き込めない
- 再現手順: 上記の順にスクリプトを実行
- 影響がありそうなモジュール: `e2e/scripts/run-suite.sh`・`e2e/scripts/a05-load-large.sh`(テストの手順)
- テスト指示との矛盾の疑い: あり(指示 A05 の【事前準備】の `docker compose cp` 手順が、api イメージを非 root(uid 10001)で動かす U006-T1 の決定と整合していない。コピー後に所有者を変える手順が必要)
- 次工程への申し送り: P202 で -g のパターンと、コピー後の所有者の変更を計画する。環境は手作業で所有者を直して HR に戻した(`docker compose run --user root ... chown 10001:10001` → api 再起動 → refresh で 7 表)
